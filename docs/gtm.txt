aft.page — growth experiments
Updated: 2026-08-10

Internal backlog of growth bets. Distribution is the constraint, not the product
(see STRATEGY.md + plan.md). Every experiment must feed the core wedge —
agent output -> durable, permissioned URL -> shared like a Google Doc — not
spin up a second product.

How to use this file
- Add ideas freely to BACKLOG. Keep each one to the 5-line shape below.
- Pull one or two into RUNNING at a time. Do not run five at once.
- When done, move to DONE with the result (kept / killed + the number).
- Each experiment:
    Hypothesis : if we do X, then metric Y moves, because Z.
    Build      : smallest thing to test it (hours/days, not weeks).
    Metric     : the ONE number that says it worked (tie to METRICS.md).
    Effort     : S (hours) / M (a day) / L (multi-day).
    Status     : idea / running / kept / killed.

North-star growth metrics (from plan.md scoreboard)
- Stranger deploys reaching a working URL   (activation)
- Time-to-URL p50/p95 on ops.aft.page every day (machine clock; see time-to-url.txt)
- Repeat deployers / apps used after 7 days (retention = the real proof)
- Apps shared with another person           (Google-Doc loop)
- Plugin installs -> first deploy in Cursor  (distribution)

--- Theme: agent-native build process (how we ship — and what we teach) ---

# Anti-pattern we reject
#   "I want everything in one prompt → plan → do."
# That produces sprawl, weak taste, and PRs nobody reviewed visually.
# Default loop instead: generate options → approve/disapprove on a page →
# learn → implement only Approves. Same spirit as the product (a URL you
# open and decide on). See STRATEGY.md § Visual review + brand-board.html.

G16. Suggest-5 / Approve-Kill boards (experimental)  [RECOMMENDED PROCESS]
    Hypothesis : if agents always draft ~5 concrete options on an HTML board
                 with Approve / Disapprove (Kill), humans decide in-page, and
                 we only implement Approves + keep a decision receipt, then
                 (a) brand/UI quality rises, (b) OSS contributors can review
                 without chat archaeology, (c) the public process becomes a
                 distribution story ("this is how agent webdev should work").
    Build      : codify the loop for design + small product UI:
                   1) Agent generates 5 specimens on a noindex HTML board
                      (or dated board under www/).
                   2) Human Approve / Disapprove in page; export markdown.
                   3) Agent implements Approves only; archive receipt in docs/.
                   4) Kills + notes become constraints for the next suggest-5.
                 First proof: brand-board.html + docs/brand-board-2026-08-08.md.
                 Next: reuse the pattern for favicon board, hero CTA copy, etc.
    Metric     : boards completed with export; % of UI PRs that cite a board
                 receipt; qualitative: fewer "redo the whole thing" turns.
    Effort     : S ongoing (process), M if we productize a reusable board kit.
    Status     : running (brand board shipped; expand beyond brand).

G17. Public "how we decide" write-up / demo for OSS builders
    Hypothesis : publishing the suggest-5 + approve-on-HTML loop (with a live
                 board URL) attracts builders who hate one-shot agent messes,
                 and positions aft as the place that ships that way.
    Build      : short post or /docs page + link to brand-board; one clip of
                 Approve → export → PR. Only after G16 has 2–3 receipts.
    Metric     : referral / GH stars / plugin interest from the post.
    Effort     : S. Status : idea (blocked on more board receipts).
